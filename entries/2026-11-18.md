## Top Thing to Implement Right Now

**ONE ACTION → turn on Row-Level Security for the open table in Supabase project "Chris" → DO TODAY.**

**HIGH LEVERAGE:** This isn't a news story. It's an open door in your own account. Supabase's weekly advisor (issues as of Nov 14) flags `rls_disabled_in_public`: anyone with the project URL (`hiooazsxwtkmetiwdbeo`) can read, edit and delete every row in that table. The Supabase URL ships inside any client app that uses it, and today's Grok Build numbers show attackers find these through DNS. It takes 10 minutes.

1. Don't click the email link. Sign in at supabase.com, open project **Chris** → **Advisors** → **Security**, and note the table name.
2. In the SQL editor (replace `your_table`):

```sql
alter table public.your_table enable row level security;

-- If the app's signed-in users should only see their own rows:
create policy "owner can read" on public.your_table
  for select using (auth.uid() = user_id);
create policy "owner can write" on public.your_table
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

3. If nothing client-side should touch the table, stop after the `enable` line. With RLS on and no policies, only the service-role key can read it.
4. Reload the app to confirm it still works, then re-run Advisors until the warning clears.
5. If the table held anything sensitive while open, rotate the project's anon key (Settings → API).
